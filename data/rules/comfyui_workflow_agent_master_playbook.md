# COMFYUI WORKFLOW AGENT — MASTER PLAYBOOK

**Версия:** 1.0  
**Статус:** рабочий master-document для основного агента  
**Назначение:** это первичный опорный документ. Агент обязан читать его первым перед началом работы по проекту.

---

## 1. Роль документа

Этот документ является **источником истины** для агента, который работает с ComfyUI, workflow-сборкой, запуском задач, контролем качества и браковкой результатов.

Агент обязан:

1. Сначала сверяться с этим документом.
2. Не менять архитектурную ось проекта без явного разрешения.
3. Работать по фазам: сначала закрывать слой целиком, потом переходить дальше.
4. Не раздувать проект в платформу ради платформы.
5. Предлагать решения, которые реально применимы на текущем железе и в текущем стеке.

---

## 2. Главная цель проекта

Нужен **личный автономный агент под ComfyUI**, который:

- умеет принимать ТЗ;
- умеет выбирать или собирать workflow под задачу;
- запускает workflow в локальном ComfyUI;
- контролирует выполнение;
- тестирует и оценивает результат;
- отправляет некачественный результат в брак;
- умеет делать ограниченный auto-retry с исправлением параметров;
- сохраняет историю запусков, ошибок, удачных профилей и причин брака.

Это **не коммерческая платформа**, не SaaS и не перегруженная мультисервисная система.  
Это **практичный personal tool**, который должен быстро работать и быть управляемым.

## 3. Жёсткие рамки проекта

### 3.1. Что входит

- Локальный ComfyUI как runtime.
- Локальный Comfy-Cozy как вспомогательный copilot / UI-слой.
- LLM через OpenRouter.
- Роутинг между несколькими моделями по типу задачи.
- Шаблонная сборка workflow.
- Валидация перед запуском.
- Мониторинг выполнения.
- Контроль качества результата.
- Браковка и retry-loop.
- Сохранение metadata, артефактов, причин решений и отчётов.

### 3.2. Что не входит на текущем этапе

- Раздувание проекта до enterprise/SaaS.
- Telegram, FastAPI, облачный прод, multi-tenant.
- Сразу сложная R&D-ветка с полным генератором графов с нуля.
- Универсальный агент «на всё».
- Переусложнение инфраструктуры микросервисами.
- Преждевременный уход в Copilot, MCP, refiner-first, multi-cloud.

- **Comfy-Cozy локально** — интерфейсный и exploratory слой, не источник истины.

### 4.3. Текущее состояние ядра

Текущий MVP уже доказал, что базовый SDXL runtime работает:

- raw prompt;
- rewrite prompt;
- OpenRouter rewrite;
- generation;
- PNG output;
- metadata JSON.

Следующий базовый слой ядра — единый `generation_service`, пресеты и нормальные статусы исполнения.

## 5. Архитектурная ось

Проект строится вокруг 4 базовых контуров:

1. **Execution Core** — запускает workflow и возвращает результат.
2. **Agent Brain** — думает, выбирает стратегию и вызывает инструменты.
3. **Quality Loop** — проверяет, принимает, бракует, инициирует retry.
4. **Operator Layer** — даёт человеку понятный вход, отчёт и контроль.

Ключевая идея:  
**ComfyUI исполняет. Агент думает. Контур качества судит. Человек утверждает направление.**

## 6. Роли компонентов

### 6.1. ComfyUI
Источник истины по исполнению workflow.  
Он не «думает», а исполняет граф, принимает его в очередь, отдает статус и историю.

### 6.2. Comfy-Cozy
Не ядро, а вспомогательный слой для:

- conversational authoring;
- exploratory control;
- просмотра и правки workflow;
- удобной ручной коррекции.

### 6.3. Python orchestrator
Главный фактический агент проекта.  
Именно он должен:

- получать задачу;
- выбирать шаблон;
- мутировать workflow;
- валидировать;
- запускать;
- наблюдать;
- оценивать;
- браковать;
- повторять попытку при необходимости.

### 6.4. OpenRouter
Транспорт к внешним моделям.  
Через него агент выбирает подходящий мозг под тип задачи и уровень сложности.

## 7. Главный принцип построения

### 7.1. Не генерировать всё с нуля без нужды
Сначала агент должен работать через:

- каталог шаблонов;
- пресеты;
- правила мутации;
- workflow registry.

### 7.2. Сборка workflow идёт так
1. Выбрать тип задачи.
2. Найти подходящий шаблон.
3. Изменить нужные узлы.
4. Проверить валидность графа.
5. Проверить наличие моделей и нод.
6. Проверить ограничения железа.
7. Только потом отправить в ComfyUI.

### 7.3. Полная генерация графа с нуля
Разрешена только как отдельная продвинутая ветка, после стабилизации шаблонного пути.

## 8. Финальная логическая схема

### 8.1. Контуры

- **Task Intake**
- **Task Classification**
- **Model Routing**
- **Workflow Registry**
- **Planner**
- **Workflow Mutator**
- **Preflight Validation**
- **Execution**
- **Runtime Monitoring**
- **Artifact Collection**
- **Quality Judging**
- **Reject / Retry**
- **Memory & Reports**

### 8.2. Логика работы

1. Пользователь передаёт ТЗ.
2. Агент классифицирует задачу.
3. Агент выбирает LLM под сложность.
4. Агент выбирает workflow template.
5. Агент строит plan изменений.
6. Агент валидирует workflow.
7. Агент запускает workflow в ComfyUI.
8. Агент отслеживает очередь и выполнение.
9. Агент получает артефакты.
10. Агент оценивает результат.
11. Если результат подходит — PASS.
12. Если результат плохой — REJECT или RETRY.
13. Агент сохраняет весь run и отчёт.

## 9. Execution Core

### 9.1. Назначение
Execution Core — это минимальное стабильное ядро, которое обязано работать всегда.

### 9.2. Минимальные обязанности ядра

- загрузить workflow template;
- подставить параметры;
- отправить workflow в ComfyUI;
- ждать completion;
- собирать артефакты;
- сохранять metadata;
- возвращать единый result object.

### 9.3. Минимальные модули

- `app/comfy/comfy_client.py`
- `app/templates/..._workflow_builder.py`
- `app/services/generation_service.py`
- `app/services/run_metadata.py`

### 9.4. Обязательные статусы

- `QUEUED`
- `RUNNING`
- `COMPLETED`
- `FAILED`
- `REJECTED`
- `RETRYING`

## 10. Agent Brain

### 10.1. Задача слоя
Преобразовать человеческое ТЗ в исполнимое действие.

### 10.2. Подмодули

- `task_classifier`
- `model_router`
- `planner`
- `workflow_selector`
- `workflow_mutator`
- `repair_planner`
- `retry_controller`

### 10.3. Что делает Agent Brain

- понимает цель задачи;
- понимает тип desired output;
- определяет сложность;
- выбирает LLM;
- выбирает workflow;
- строит mutation plan;
- предлагает repair strategy после неудачи.

### 10.4. Что Agent Brain не делает
Он не должен напрямую писать хаотичный workflow в прод без:

- registry;
- validator;
- resource check;
- explicit repair logic.

---

## 11. Workflow Registry

### 11.1. Назначение
Это база знаний агента о workflow, моделях, пресетах и совместимых связках.

### 11.2. Хранить в registry

- каталог workflow templates;
- типы задач;
- поддерживаемые checkpoints;
- VAE / LoRA / custom nodes;
- совместимые профили;
- quality profiles;
- known-good combinations;
- known-failure combinations.

### 11.3. Почему registry обязателен
Без registry агент будет:

- гадать;
- ломать графы;
- использовать недоступные узлы;
- гонять несовместимые модели;
- плодить мусорные попытки.

---

## 12. Preflight Validation

### 12.1. Главная идея
Всё сомнительное надо отсеивать **до запуска**, а не после провала.

### 12.2. Проверки

- структура workflow валидна;
- node ids корректны;
- все связи корректны;
- нужные модели реально существуют;
- нужные custom nodes существуют;
- разрешение и параметры не убивают железо;
- prompt и входные поля адекватны;
- выходной путь корректен.

### 12.3. Критерий
Если preflight не проходит — workflow не запускается.

---

## 13. Runtime Monitoring

### 13.1. Что обязан видеть агент

- постановку в очередь;
- старт выполнения;
- завершение;
- ошибку;
- сведения из history;
- наличие файлов результата.

### 13.2. Источники данных

- очередь;
- websocket-события;
- history;
- output artifacts;
- локальные metadata.

### 13.3. Главное правило
Агент не должен делать вид, что задача выполнена, пока:

- не получил подтверждение completion;
- не нашёл артефакт;
- не собрал базовый отчёт.

---

## 14. Quality Loop

### 14.1. Это обязательный контур
Агент не должен просто запускать workflow. Он обязан судить результат.

### 14.2. Три уровня оценки

#### Technical QA
Проверяет:

- есть ли файл;
- не битый ли он;
- совпадает ли размер;
- не пустой ли output;
- не развален ли результат технически.

#### Semantic QA
Проверяет:

- соответствует ли результат ТЗ;
- есть ли ключевой объект;
- совпадает ли тип сцены;
- не потеряна ли обязательная деталь.

#### Aesthetic QA
Проверяет:

- целостность изображения;
- убедительность света;
- отсутствие сильного AI-look;
- читаемость композиции;
- общую пригодность к использованию.

### 14.3. Выход judge layer

- `PASS`
- `PASS_WITH_NOTES`
- `RETRY`
- `REJECT`

---

## 15. Критерии брака

### 15.1. Брак обязателен, если

- файл не создан;
- файл битый или пустой;
- не тот размер;
- отсутствует ключевой объект;
- сцена не соответствует ТЗ;
- сильные артефакты лица / рук / геометрии;
- результат технически или семантически непригоден.

### 15.2. Не полный брак, а замечания

- лёгкие косметические дефекты;
- результат рабочий, но не лучший;
- можно усилить свет, композицию, детали или соответствие стилю.

### 15.3. Формула решения
Если результат нельзя использовать по назначению — это **REJECT**, а не «ну почти».

---

## 16. Retry / Repair Loop

### 16.1. Retry — не бесконечный
Максимум 2–3 автоматических итерации на задачу.

### 16.2. Разрешённые repair-действия

- prompt rewrite;
- смена negative prompt;
- смена sampler;
- смена scheduler;
- изменение steps;
- изменение CFG;
- seed cycling;
- смена пресета;
- переход на другой шаблон;
- отключение проблемной ветки workflow.

### 16.3. Запрещено
Делать бесконечные прогоны без понятной repair-логики.

---

## 17. Memory & Learning

### 17.1. Агент должен помнить

- какие workflow давали хороший результат;
- какие настройки ломают задачу;
- какие типы брака повторяются;
- какие repair-паттерны помогают.

### 17.2. Минимальное хранилище

- локальная база запусков;
- JSON metadata;
- judge reports;
- known failures;
- known good profiles.

### 17.3. Цель памяти
Не делать одну и ту же глупость десять раз подряд.

## 18. Политика роутинга моделей

| Ситуация | Модель | Назначение |
|---|---|---|
| Дешёвый дефолт | `google/gemini-2.5-flash-lite` | классификация задачи, rewrite, простые преобразования |
| Основной мозг | `openai/gpt-4.1-mini` | planner, tool calling, mutation, рабочий orchestration |
| Сложный workflow | `qwen/qwen3.6-plus` | более уверенный synthesis, repair, сложная логика |
| Reasoning-heavy режим | `google/gemini-2.5-flash` | разбор трудных случаев, сложные repair-решения |

### 18.1. Правило выбора модели
Нельзя по умолчанию гонять самые дорогие модели на каждую задачу.  
Роутинг обязан учитывать:

- сложность;
- стоимость;
- срочность;
- тип задачи;
- потребность в reasoning.

## 21. Definition of Done

Агент считается готовым, когда он умеет:

1. Принять ТЗ.
2. Определить тип задачи.
3. Выбрать LLM.
4. Выбрать workflow template.
5. Построить mutation plan.
6. Провести preflight validation.
7. Запустить workflow.
8. Отследить статус.
9. Получить артефакты.
10. Оценить качество.
11. Принять / отклонить результат.
12. Выполнить ограниченный retry.
13. Сохранить историю и отчёт.

Если хотя бы один из этих блоков отсутствует — агент ещё не финальный.

## 23. Правила поведения агента

Агент обязан:

- работать фазами;
- не прыгать по архитектуре;
- сначала закрывать слой целиком;
- затем переходить к следующему;
- давать честный вывод;
- не скрывать провалы;
- не выдавать «почти» за успех;
- явно обозначать риски, стоимость и сложность;
- не раздувать проект без команды.

Агенту запрещено:

- тащить лишние технологии без необходимости;
- предлагать enterprise-решения ради красоты;
- менять главный стек без разрешения;
- игнорировать quality gate;
- игнорировать reject logic;
- запускать workflow без preflight, если слой уже реализован.

## 24. Порядок работы агента на практике

### Каждый новый заход по задаче должен идти так:

1. Прочитать этот документ.
2. Определить, к какой фазе относится текущая задача.
3. Проверить, не ломает ли задача архитектурную ось.

5. Сформулировать, какой результат должен быть получен на выходе слоя.
6. После закрытия слоя свериться с общим планом.
7. Только потом идти дальше.
